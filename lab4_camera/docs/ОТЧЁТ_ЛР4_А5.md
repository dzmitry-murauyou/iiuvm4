## 1. Цель работы

Изучить архитектуру подсистем видеозахвата ОС Windows, освоить программные
интерфейсы обнаружения, идентификации и управления веб-камерами; получить
практические навыки разработки приложений на C++ для получения, отображения и
сохранения видеопотока в реальном времени с использованием низкоуровневых
системных API (DirectShow / Media Foundation) и научиться реализовывать
фоновый режим наблюдения, журналирование событий и управление горячими
клавишами.

## 2. Задание (вариант А5)

Реализовать приложение с возможностью фонового создания снимков:

1. главное окно приложения со всеми элементами базового монитора;
2. кнопка «Свернуть в трей» — скрытие окна, оставление иконки в системном трее
   (`Shell_NotifyIcon`);
3. регистрация глобальной горячей клавиши (`RegisterHotKey`, например
   `Ctrl+Shift+F12`) для создания снимка без отображения окна;
4. при нажатии горячей клавиши в фоновом режиме — захват кадра с камеры и
   сохранение в выбранный каталог с именем `snapshot_YYYYMMDD_HHMMSS.jpg`;
5. всплывающее уведомление (balloon tip) об успешном сохранении снимка;
6. восстановление главного окна по двойному клику на иконке в трее;
7. журналирование всех фоновых операций.

## 4. Архитектура приложения

```
                    ┌──────────────────────────────────────────┐
                    │           Главное окно (Win32)           │
                    │  заголовок: индикатор состояния + REC    │
                    │  ┌──────────────────┐ ┌────────────────┐ │
                    │  │  предпросмотр    │ │   устройство   │ │
                    │  │  (StretchDIBits) │ │  инфо + кнопки │ │
                    │  └──────────────────┘ └────────────────┘ │
                    │  ┌──────────────────┐ ┌────────────────┐ │
                    │  │  сохранение      │ │  журнал событий│ │
                    │  └──────────────────┘ └────────────────┘ │
                    └───────┬───────────────┬──────────────────┘
                            │ WM_APP_FRAME  │ WM_APP_STATE
                            │ WM_APP_LOG    │ WM_HOTKEY / WM_APP_TRAY
                            ▼               ▼
                 ┌──────────────────────────────────────────┐
                 │           CaptureController              │
                 │  поток захвата (std::thread)             │
                 │  ICamera: CameraOpenCV | CameraMF        │
                 │  последний кадр + кольцевой буфер        │
                 └───────┬──────────────────────┬───────────┘
                         │ кадры                │ устройства
                         ▼                      ▼
                 ┌───────────────┐      ┌──────────────────┐
                 │ VideoRecorder │      │  DeviceMonitor   │
                 │ AVI / MJPEG   │      │ WM_DEVICECHANGE  │
                 └───────────────┘      └──────────────────┘
```

Ключевые решения:

* **GUI-поток никогда не вызывает камеру напрямую.** Поток захвата кладёт
  кадр в `latest_` (под мьютексом) и посылает окну `WM_APP_FRAME`; окно берёт
  копию кадра при отрисовке. Это исключает подвисания интерфейса на
  блокирующем `read()`/`ReadSample()`.
* **Единый интерфейс `ICamera`** для двух бэкендов — переключение без
  изменения GUI и логики сохранения.
* **Кольцевой буфер `FrameQueue`** между захватом и записью: при
  переполнении отбрасывается самый старый кадр, поэтому задержка записи не
  растёт неограниченно.
* **Состояние камеры** (`Disconnected / Connecting / Connected / Error`)
  передаётся в GUI сообщением `WM_APP_STATE` и отображается цветным
  индикатором.

## 5. Реализация по пунктам задания

### 5.1. Обнаружение устройств и информация о них

Перечисление выполняется через Media Foundation (не открывает поток и потому
безопасно при работающем захвате):

```cpp
IMFAttributes* attributes = nullptr;
MFCreateAttributes(&attributes, 1);
attributes->SetGUID(MF_DEVSOURCE_ATTRIBUTE_SOURCE_TYPE,
                    MF_DEVSOURCE_ATTRIBUTE_SOURCE_TYPE_VIDCAP_GUID);
MFEnumDeviceSources(attributes, &devices, &count);

for (UINT32 i = 0; i < count; ++i) {
    WCHAR* name = nullptr; UINT32 length = 0;
    devices[i]->GetAllocatedString(MF_DEVSOURCE_ATTRIBUTE_FRIENDLY_NAME, &name, &length);
    ...
}
```

Имя устройства из MF используется и для бэкенда OpenCV: `cv::VideoCapture`
на Windows не отдаёт «человеческое» имя камеры.

Поддерживаемые режимы (разрешение, FPS, пиксельный формат) для бэкенда MF
читаются через `IMFMediaTypeHandler`/`GetNativeMediaType` (`MF_MT_FRAME_SIZE`,
`MF_MT_FRAME_RATE`, `MF_MT_SUBTYPE`), для бэкенда OpenCV — через
`CAP_PROP_FRAME_WIDTH/HEIGHT/FPS/FOURCC`.

### 5.2. Предпросмотр в реальном времени

```cpp
BITMAPINFO bmi{};
bmi.bmiHeader.biSize = sizeof(BITMAPINFOHEADER);
bmi.bmiHeader.biWidth = frame.width;
bmi.bmiHeader.biHeight = -frame.height;   // top-down
bmi.bmiHeader.biPlanes = 1;
bmi.bmiHeader.biBitCount = 24;
bmi.bmiHeader.biCompression = BI_RGB;

SetStretchBltMode(dc, HALFTONE);
StretchDIBits(dc, x, y, w, h, 0, 0, frame.width, frame.height,
              frame.pixels.data(), &bmi, DIB_RGB_COLORS, SRCCOPY);
```

Кадр хранится как BGR24 (`CameraFrame`), пропорции сохраняются
(letterbox), в левом нижнем углу выводится дата и время.

### 5.3. Снимок кадра

Имя файла формируется по шаблону `snapshot_YYYYMMDD_HHMMSS.jpg`; при
совпадении секунд добавляется суффикс `_1`, `_2`:

```cpp
std::wstring base = join_path(dir, L"snapshot_" + file_timestamp(st)); // 20261028_183012
while (file_exists(candidate)) candidate = base + L"_" + std::to_wstring(counter++) + L".jpg";
```

Сохранение: `cv::imwrite` с качеством из настройки (1–100). Если JPEG-кодировщик
недоступен — резервная запись BMP вручную:

```cpp
BITMAPFILEHEADER fh{}; BITMAPINFOHEADER ih{};
fh.bfType = 0x4D42;                       // "BM"
ih.biBitCount = 24; ih.biCompression = BI_RGB; ih.biHeight = height; // bottom-up
// далее построчная запись BGR с выравниванием строки по 4 байтам
```

### 5.4. Запись видео

`VideoRecorder` — отдельный поток, который берёт кадры из `FrameQueue` и
пишет AVI/MJPEG:

```cpp
writer.open(path, cv::VideoWriter::fourcc('M','J','P','G'), fps, cv::Size(w, h));
...
while (!stop_requested_.load()) {
    CameraFrame frame;
    if (!queue_->pop(frame, 300)) continue;
    cv::Mat mat(frame.height, frame.width, CV_8UC3, frame.pixels.data(), frame.stride);
    if (mat.size() != cv::Size(width_, height_)) resize(mat, mat, ...);
    writer.write(mat);
}
```

По остановке в журнал пишется длительность, число кадров, размер файла.

### 5.5. Скрытый режим: трей

```cpp
void App::hide_to_tray() {
    if (state_ != CameraState::Connected && !devices_.empty())
        connect_camera();                       // фоновый режим = камера работает
    ShowWindow(hwnd_, SW_HIDE);
    minimized_to_tray_ = true;
    add_log(LogLevel::Background, L"Окно свёрнуто в трей — работает фоновое фотонаблюдение");
    show_balloon(L"Фотонаблюдение включено", L"Ctrl+Shift+F12 — снимок без окна", NIIF_INFO);
}
```

Значок добавляется один раз при запуске:

```cpp
NOTIFYICONDATAW data{};
data.cbSize = sizeof(data);
data.hWnd = hwnd_;  data.uID = 1;
data.uFlags = NIF_ICON | NIF_MESSAGE | NIF_TIP;
data.uCallbackMessage = WM_APP_TRAY;
Shell_NotifyIconW(NIM_ADD, &data);
```

Обработка событий значка: `WM_LBUTTONDBLCLK` → `restore_window()`,
`WM_RBUTTONUP` → контекстное меню (показать окно / снимок / запись / выход).

### 5.6. Глобальная горячая клавиша и снимок в фоне

```cpp
hotkey_registered_ = RegisterHotKey(hwnd_, HOTKEY_SNAPSHOT,
                                    MOD_CONTROL | MOD_SHIFT, VK_F12) != FALSE;

// ... в оконной процедуре
case WM_HOTKEY:
    on_hotkey(static_cast<int>(wParam));   // -> take_snapshot(true)
```

`take_snapshot(true)`:

1. берёт **последний** кадр из `CaptureController` (камера уже открыта —
   задержка минимальна, повторное открытие устройства не требуется);
2. сохраняет JPEG в выбранный каталог;
3. пишет в журнал запись уровня `BACKGROUND`;
4. показывает balloon tip с именем файла и каталогом.

Если сигнала нет — выводится предупреждение (`NIIF_WARNING`) и запись в журнал
об ошибке; приложение при этом не падает.

### 5.7. Журналирование

`Logger` — потокобезопасный синглтон: хранит до 5000 записей в памяти,
немедленно дописывает каждую строку в `camera_log.txt` (UTF-8 с BOM) и
уведомляет GUI через колбэк (тот пересылает `WM_APP_LOG`). Уровни:
`INFO`, `WARN`, `ERROR`, `BACKGROUND` (события скрытого режима выделены цветом).
Кнопка «Сохранить отчёт» выгружает журнал в `report_YYYYMMDD_HHMMSS.txt`.

### 5.8. Контроль состояния камеры

Два независимых механизма:

1. окно получает `WM_DEVICECHANGE` (`RegisterDeviceNotification` с
   `GUID_DEVINTERFACE_IMAGE`) и инициирует внеочередной опрос;
2. `DeviceMonitor` раз в 3 с перечисляет устройства и сравнивает списки по
   уникальным идентификаторам (`describe_device_changes`), сообщая
   «подключена камера: …» / «отключена камера: …».

Если кадры перестают приходить (камеру выдернули), поток захвата после 20
неудачных попыток закрывает устройство и пытается открыть его снова
(автопереподключение, включается флажком).

### 5.9. Интерфейс

Главное окно (Win32, без MFC/Qt): заголовок с индикатором состояния и
мигающим индикатором записи, область предпросмотра с датой/временем, панель
устройства (камера, разрешение, FPS, бэкенд, качество JPEG, кнопки

## 7. Выводы

В ходе работы изучены подсистемы видеозахвата Windows (DirectShow и Media
Foundation) и механизмы перечисления устройств (`MFEnumDeviceSources`,
`IMFActivate`, `IPropertyBag`). Разработано приложение на C++/Win32, которое
захватывает видеопоток, отображает его в реальном времени, сохраняет снимки
(JPEG/BMP) и видео (AVI/MJPEG), ведёт журнал с временными метками и умеет
работать в скрытом режиме: окно сворачивается в трей, глобальная горячая
клавиша `Ctrl+Shift+F12`, зарегистрированная через `RegisterHotKey`, создаёт
снимок без открытия окна, результат подтверждается всплывающим уведомлением
`Shell_NotifyIcon(NIF_INFO)`.

Основные технические выводы:

* захват необходимо выполнять в отдельном потоке, а GUI уведомлять
  сообщениями (`PostMessage`), иначе блокирующее чтение кадра «подвешивает»
  интерфейс;
* кадр удобно хранить в BGR24 — этот формат одинаково понимают GDI
  (`StretchDIBits` с 24 битами на пиксель) и OpenCV (`cv::Mat`, `imwrite`,
  `VideoWriter`);
* для фонового режима камеру нельзя закрывать при скрытии окна — иначе
  теряется смысл «мгновенного» снимка по горячей клавише;
* `RegisterHotKey` надёжнее низкоуровневого хука клавиатуры: не требует
  отдельного потока с циклом сообщений и не вызывает подозрений у антивирусов;
* перечисление устройств через Media Foundation не открывает поток, поэтому
  безопасно при активном захвате (в отличие от повторного `cv::VideoCapture::open`).

## 8. Ответы на контрольные вопросы

**1. Подсистемы видеозахвата в Windows, их отличия.**
DirectShow — фильтровая архитектура (Filter Graph): источники, трансформации,
рендереры, граф собирается через `ICaptureGraphBuilder2`. Media Foundation —
более современный API (с Vista/7), конвейерная модель (Source Reader →
Transform → Sink Writer), лучше поддерживает аппаратное ускорение и
кодирование (H.264/AAC), рекомендован Microsoft для новых приложений.
DirectShow проще для legacy-устройств, MF — для записи/кодирования и
современного оборудования.

**2. Перечисление устройств через `CLSID_SystemDeviceEnum`.**
`CoCreateInstance(CLSID_SystemDeviceEnum, …)` создаёт `ICreateDevEnum`;
`CreateClassEnumerator(CLSID_VideoInputDeviceCategory, &pEnum, 0)` даёт
`IEnumMoniker` для категории «устройства видеозахвата»; `IEnumMoniker::Next`
возвращает `IMoniker` каждого устройства — это именованный объект COM,
представляющий устройство. `IMoniker::BindToStorage(…, IID_IPropertyBag, …)`
даёт свойства (`FriendlyName`, `DevicePath`), `IMoniker::BindToObject` —
сам фильтр-источник. Все интерфейсы освобождаются `Release()`.

**3. Список разрешений, FPS и форматов.**
DirectShow: `ICaptureGraphBuilder2::FindInterface` → `IAMStreamConfig`;
`GetNumberOfCapabilities`, затем `GetStreamCaps(i, &pmt, &caps)` —
`caps.InputSize` (разрешение), `caps.MinFrameInterval/MaxFrameInterval`
(100-нс интервалы), `pmt->subtype` (RGB24, MJPG, YUY2). Media Foundation:
`IMFMediaSource::CreatePresentationDescriptor` → `IMFStreamDescriptor` →
`IMFMediaTypeHandler`; `GetMediaTypeCount` и `GetMediaTypeByIndex`, далее
`MFGetAttributeSize(MF_MT_FRAME_SIZE)`, `MFGetAttributeRatio(MF_MT_FRAME_RATE)`,
`GetGUID(MF_MT_SUBTYPE)`.

**4. Форматы пикселей.**
RGB24 — 3 байта/пиксель, прост в обработке, но большой трафик.
YUY2 — 2 байта/пиксель (4:2:2), требует конвертации в RGB для отображения.
NV12 — 1.5 байта/пиксель (4:2:0), типичен для H.264-конвейеров.
MJPEG — сжатый кадр (обычно 5–15 % от RAW), максимальное разрешение при
ограниченной пропускной способности USB, но декодирование всё равно нужно.
Для 1280×720: RGB24 ≈ 2.7 МБ/кадр, YUY2 ≈ 1.8 МБ, NV12 ≈ 1.4 МБ;
MJPEG-кадр — сотни килобайт.

**5. Захват отдельного кадра.**
DirectShow — Sample Grabber (`ISampleGrabber::SetBufferSamples`,
`SetCallback`), буфер копируется в `GetBuffer`. Media Foundation —
`IMFSourceReader::ReadSample(…, &pSample)`, затем
`ConvertToContiguousBuffer` и `Lock` для доступа к RAW-данным. В работе
используется второй вариант (бэкенд Media Foundation), а в OpenCV-бэкенде —
эквивалент `cv::VideoCapture::read`.

**6. Сохранение кадра в BMP/JPEG без сторонних библиотек.**
BMP: сформировать `BITMAPFILEHEADER` (`"BM"`, смещение данных) и
`BITMAPINFOHEADER` (24 бита, `BI_RGB`), затем построчно записать BGR снизу
вверх с выравниванием строки до 4 байт. JPEG «вручную» — это реализация
DCT-кодировщика (нецелесообразно); поэтому в работе JPEG пишется через
OpenCV, а BMP — своим кодом (`FrameConvert::write_bmp`), что и демонстрирует
понимание формата.

**7. Запись видео через `IMFSinkWriter`.**
`MFCreateSinkWriterFromURL(L"out.mp4", …)`; для видео-потока создать
выходной тип (`MF_MT_MAJOR_TYPE = MFMediaType_Video`,
`MF_MT_SUBTYPE = MFVideoFormat_H264`, размер, FPS, битрейт) и добавить поток
(`AddStream`); задать входной тип (`SetInputMediaType`); вызывать
`WriteSample` с `IMFSample` (метка времени `MFSampleExtension_*`,
`SetSampleDuration`); в конце — `Finalize`.

**8. Отслеживание подключения/отключения камеры.**
`RegisterDeviceNotification` с `DEV_BROADCAST_DEVICEINTERFACE`
(`GUID_DEVINTERFACE_IMAGE`) регистрирует окно на уведомления; система посылает
`WM_DEVICECHANGE` с `wParam = DBT_DEVICEARRIVAL` / `DBT_DEVICEREMOVECOMPLETE` /
`DBT_DEVNODES_CHANGED`. В обработчике перечисляется список устройств и
обновляется интерфейс; `UnregisterDeviceNotification` — при завершении.

**9. Скрытый режим, трей и горячие клавиши.**
Скрытый режим — приложение продолжает работать без видимого окна:
`ShowWindow(hwnd, SW_HIDE)` + значок `Shell_NotifyIcon(NIM_ADD)` с
`uCallbackMessage`, контекстным меню и balloon tip. Глобальная клавиша —
`RegisterHotKey(hwnd, id, MOD_CONTROL|MOD_SHIFT, VK_F12)`, событие приходит
как `WM_HOTKEY` с идентификатором в `wParam`; снимается
`UnregisterHotKey`. Окно при этом обязано обрабатывать сообщения (что и делает
цикл `GetMessage/DispatchMessage`).

**10. Привилегии и разрешения.**
Специальных прав администратора не нужно, но с Windows 10 доступ к камере
управляется параметром конфиденциальности («Параметры → Конфиденциальность →
Камера»): пользователь разрешает доступ приложениям и классическим
Win32-программам. Это защита приватности: камера — чувствительное устройство,
и ОС не позволяет приложениям снимать видео без ведома пользователя. При
отказе в доступе `open`/`ActivateObject` завершается ошибкой, которую
приложение показывает в журнале.

**11. Video4Linux2 и системные вызовы.**
V4L2 — драйверный интерфейс ядра Linux для устройств видео. Взаимодействие:
`open("/dev/videoN")`, настройка через `ioctl` (`VIDIOC_QUERYCAP`,
`VIDIOC_S_FMT`, `VIDIOC_REQBUFS`, `VIDIOC_QBUF`, `VIDIOC_DQBUF`,
`VIDIOC_STREAMON`), буферы отображаются в память через `mmap`, обмен идёт
через `poll`/`select`, освобождение — `munmap`/`close`.

**12. `VIDIOC_QUERYCAP`.**
Заполняет `struct v4l2_capability`: `driver` — имя драйвера (например,
`uvcvideo`), `card` — имя устройства («USB Camera»), `bus_info` — шина
(«usb-0000:00:14.0-5»), `version`, `capabilities` (проверка
`V4L2_CAP_VIDEO_CAPTURE`, `V4L2_CAP_STREAMING`).

**13. Форматы, разрешения и FPS в V4L2.**
`VIDIOC_ENUM_FMT` (`v4l2_fmtdesc`: `pixelformat`, `description`) —
форматы; для каждого формата `VIDIOC_ENUM_FRAMESIZES`
(`v4l2_frmsizeenum.discrete.width/height`) — разрешения; для каждой пары
`VIDIOC_ENUM_FRAMEINTERVALS`
(`v4l2_frmivalenum.discrete.numerator/denominator`) — интервалы, FPS =
denominator/numerator. Перечисление завершается, когда ioctl возвращает
`EINVAL`; индекс увеличивается вручную.

**14. Захват через mmap.**
`VIDIOC_REQBUFS` (count, `V4L2_MEMORY_MMAP`) → для каждого буфера
`VIDIOC_QUERYBUF` + `mmap` → `VIDIOC_QBUF` (поставить в очередь) →
`VIDIOC_STREAMON` → ожидание `poll` → `VIDIOC_DQBUF` (получить индекс и
`bytesused`) → обработка данных в `buffers[buf.index]` → снова `VIDIOC_QBUF`.
Завершение: `VIDIOC_STREAMOFF`, `munmap`, `close`.

**15. Сохранение MJPEG / YUYV / RGB24.**
MJPEG: буфер уже содержит готовый JPEG — достаточно записать `bytesused`
байт в файл `.jpg`. YUYV: нужно преобразовать в RGB/BGR (или сохранить как
PPM/BMP, дописав заголовок), учитывая субдискретизацию яркости/цветности.
RGB24: сохранить с заголовком BMP/PPM; из-за порядка BGR/RGB и выравнивания
строк возможны перестановки байт.

**16. Запись видео в Linux без FFmpeg.**
Варианты: (1) сохранять последовательность JPEG-кадров (`frame_00001.jpg`),
затем склеивать; (2) вручную формировать AVI-контейнер (RIFF: `hdrl` с
`avih`/`strh`/`strf` для MJPG, `movi` с чанками `00dc`, затем `idx1`-индекс) —
именно так устроен MJPEG-AVI; (3) писать необработанные кадры (raw) с
последующей обработкой; (4) pipe в `ffmpeg` (допустимо как внешний инструмент,
а не как API-библиотека).

**17. Отслеживание камеры в Linux.**
udev — монитор Netlink: `udev_monitor_new_from_netlink`,
`udev_monitor_filter_add_match_subsystem_devtype("video4linux")`, `poll` по fd;
события `add`/`remove`. inotify на `/dev` (IN_CREATE/IN_DELETE) — проще, но
не даёт свойств устройства и может пропускать события. Опрос `sysfs`
(`/sys/class/video4linux/`) — самый простой, но с задержкой и нагрузкой.
udev — предпочтителен.

**18. Глобальные горячие клавиши в Linux.**
X11: `XGrabKey(display, keycode, modifiers, root, True, GrabModeAsync,
GrabModeAsync)` на корневом окне; события `KeyPress` приходят даже при
неактивном окне; нужен `XKeysymToKeycode`/`XStringToKeysym`. evdev: чтение
`/dev/input/event*` — требует root или членства в группе `input`; зато
работает без X (в консоли). В Wayland глобальные клавиши через X11-механизмы
не работают — нужны порталы (`org.freedesktop.portal.GlobalShortcuts`).

**19. Многопоточный захват с нескольких камер.**
Для каждой камеры — свой `fd`/объект `ICamera` и свой поток (или общий пул с
`poll` на нескольких fd). Кадры складываются в отдельные кольцевые буферы,
GUI отрисовывает их по сообщениям/таймеру. Проблемы: гонки при доступе к
буферам (нужны мьютексы/атомарные обмены указателей), разная частота кадров,
синхронизация временных меток, конкуренция за USB-контроллер (пропускная
способность делится между камерами), блокирующие вызовы при отключении
устройства (нужны таймауты и переподключение).

**20. Почему запрещены OpenCV/GStreamer/FFmpeg API.**
Цель работы — изучение системных API (`open/ioctl/mmap`, DirectShow/MF), а
высокоуровневые библиотеки скрывают эти механизмы. Прямое использование
системных API даёт: понимание реальных ограничений (форматы, буферы,
синхронизация), меньший размер зависимости, отсутствие «чёрного ящика» при
отладке, возможность тонкой настройки (например, выбор MJPG вместо YUY2).
В данной работе OpenCV применён только как средство захвата/кодирования по
согласованию с преподавателем; скрытый режим, трей, горячие клавиши, журнал,
мониторинг устройств и BMP-запись реализованы системными средствами, а
бэкенд Media Foundation показывает «низкоуровневый» путь захвата.
