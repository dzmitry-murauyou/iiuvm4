## 0. Как отвечать на защите: короткая линия

Три фразы, которые задают весь дальнейший разговор:

1. **«Приложение — обычное Win32-окно с собственным циклом сообщений; камера
   живёт в отдельном потоке и общается с окном только через сообщения —
   поток ни разу не трогает GUI напрямую.»**
2. **«Код разделён на два модуля: `main.cpp` — логика (камера, файлы, журнал,
   трей), `visual.cpp` — визуал (тема, шрифты, раскладка, отрисовка).
   Между ними тонкий интерфейс `visual.h` со структурами данных.»**
3. **«Всё оформление нарисовано вручную через GDI+: окно не использует
   стандартные светлые контролы, поэтому кнопки, списки и журнал —
   owner-draw.»**

Дальше по любому вопросу схема одна: **кто вызывает → что происходит →
что видит пользователь**.

│    1. тема (цвета, отступы)  2. DPI  3. помощники рисования

Почему так: логику можно менять, не открывая визуал (и наоборот). Визуал
**ничего не знает** про камеру и файлы — он получает структуру `visual::Model`
и рисует по ней.

### Поток данных

```
      ┌──────────────────── поток захвата (Camera::Run) ───────────────────┐
      │ cv::VideoCapture → cv::Mat кадра → копия в Frame (BGR, построчно)   │
      │            ↓ mutex_                                                │
      │        latest_ (последний кадр)  ──── PostMessage(WM_FRAME) ──┐    │
      │        VideoWriter (если идёт запись)                         │    │
      └───────────────────────────────────────────────────────────────┼────┘
                                                                      ▼
   главный поток: окно App ── WM_PAINT ──► camera_.Latest(frame)
                                             │
                                             ▼
                                   visual::Model  ──► View::Paint()
                                   (состояние, тексты, кадр)
```

Главный поток **никогда** не вызывает `capture.read()` — он только копирует
готовый кадр из `latest_` под мьютексом. Поэтому интерфейс не замирает.

## 3. `main.cpp`, раздел 2 — камера

### 3.1. `EnumerateCameras()` — перечисление

```cpp
CoCreateInstance(CLSID_SystemDeviceEnum, ...)        // системный перечислитель
dev_enum->CreateClassEnumerator(CLSID_VideoInputDeviceCategory, ...)
while (enum_moniker->Next(1, &moniker, nullptr) == S_OK) {
    moniker->BindToStorage(..., IID_PPV_ARGS(&bag));
    bag->Read(L"FriendlyName", &value, nullptr);     // имя камеры
    bag->Read(L"DevicePath", &value, nullptr);       // путь устройства
    VariantClear(&value);  moniker->Release();
}
```

Это классический DirectShow-путь из теории: `ICreateDevEnum` → `IEnumMoniker`
→ `IMoniker` → `IPropertyBag`. **Порядок монikers совпадает с порядком
индексов, которые использует OpenCV с бэкендом DSHOW** — поэтому индекс из
списка можно передать в `capture.open(index)`.

На защите могут сказать «а в отчёте написано SetupAPI». Правильный ответ:
перечисление через DirectShow, потому что он же используется для захвата —
индексы гарантированно совпадают.

### 3.2. `struct Frame` — кадр

```cpp
struct Frame {
    int width, height;
    std::vector<unsigned char> bgr;   // плотный BGR24, построчно
    bool ok() const { return width > 0 && height > 0 && !bgr.empty(); }
};
```

Почему не хранить `cv::Mat`: `Frame` — простая структура без внешних
зависимостей, её можно копировать и отдавать в визуал. `cv::Mat` держит
внутренний счётчик ссылок и владеет памятью — отдавать его в GUI неудобно.

### 3.3. `Camera` — класс

Публичный интерфейс (единственное, что видит GUI):

| Метод | Что делает |
|---|---|
| `Start(index, w, h, fps)` | сбрасывает старый кадр, ставит `Opening`, запускает `worker_` (поток) |
| `Stop()` | `running_ = false`, `join()`, закрывает `VideoWriter`, состояние `Off` |
| `Latest(Frame&)` | копия последнего кадра под мьютексом, `false` если кадра нет |
| `WaitForFrame(out, ms)` | **ждёт** кадр на условной переменной до `ms` |
| `StartRecording(path, fps)` / `StopRecording()` | флаги для потока захвата |
| `RecordStateValue()` | `Off / Pending / On / Failed` |
| `State()`, `MeasuredFps()`, `FormatName()` | состояние, измеренный FPS, fourcc |

### 3.4. `Run()` — поток захвата, главный метод проекта

По шагам:

1. `capture.open(index, cv::CAP_DSHOW)` — бэкенд DirectShow; если не вышло,
   повтор без указания бэкенда.
2. `CAP_PROP_FOURCC = MJPG` — просить MJPEG вместо сырого YUY2: при том же
   USB-трафике камера отдаёт большее разрешение. Затем ширина/высота/частота.
3. Первый `read()` — если кадр пустой, значит камера занята или запрещена
   в «Конфиденциальность → Камера»: `Notify(Failed, ...)` и выход.
4. Читает фактический fourcc через `CAP_PROP_FOURCC` (4 байта, разложенные
   сдвигами) — это и есть «формат» в панели сведений.
5. `Notify(On, "Камера подключена: W × H")` → окно получает `WM_STATE`.
6. Цикл `while (running_)`:
   - `read()` в `try/catch` — OpenCV кидает `cv::Exception` при сбоях;
   - пустой кадр → счётчик `failures`, после 30 подряд — выход (камеру выдернули);
   - 1 и 4 канала → `cvtColor` в BGR (камера может отдать серый или BGRA);
   - **копия в `Frame`**: если `frame.step == width*3`, можно `memcpy` всего
     буфера сразу, иначе — построчно (в `Mat` между строками бывает выравнивание);
   - `latest_ = std::move(out)` под `mutex_`, затем `frame_cv_.notify_all()`;
   - блок записи: под `record_mutex_` забирает флаги `start/stop`, открывает/
     закрывает `VideoWriter` и пишет кадр;
   - раз в секунду пересчитывает `measured_fps_`;
   - `PostMessage(hwnd_, WM_FRAME)` — «есть новый кадр».

**Почему `PostMessage`, а не `SendMessage`:** `PostMessage` складывает сообщение
в очередь и сразу возвращается — поток захвата не ждёт, пока GUI перерисуется.
`SendMessage` заблокировал бы захват на время отрисовки.

**Почему кадр копируется, а не передаётся указателем:** `cv::Mat` переиспользует
буфер при следующем `read()`; указатель стал бы висячим. Копия — цена ~2,7 МБ
на кадр 1280×720, зато без гонок.

### 3.5. Запись видео (внутри `Run`)

Отдельный нюанс: **GUI не открывает файл**. `StartRecording()` только кладёт
путь в `record_path_` и ставит `record_start_ = true`; открытие/закрытие и
`writer_.write(frame)` делает поток захвата — единственный владелец `writer_`,
поэтому мьютекс вокруг самого писателя не нужен.

Состояние: `Pending` (запросили) → `On` (файл открылся) либо `Failed`
(кодек/путь/размер кадра). Именно поэтому сообщение «Запись начата»
появляется **после** реального открытия файла, а не по нажатию кнопки.

## 4. `main.cpp`, раздел 3 — главное окно `App`

### 4.1. Каркас

```cpp
WNDCLASSEXW wc; wc.lpfnWndProc = &App::WndProc;   // статическая функция
CreateWindowExW(..., inst_, this);                // this передаём в lpParam
```

Классический приём Win32: оконная процедура должна быть статической, поэтому
`this` кладётся в `GWLP_USERDATA` при `WM_NCCREATE`, а `WndProc` достаёт его
и вызывает `self->Handle(msg, wp, lp)`.

### 4.2. `Handle()` — таблица сообщений

| Сообщение | Что делает | Зачем |
|---|---|---|
| `WM_CREATE` | `OnCreate()` | создать контролы, трей, таймеры, клавишу |
| `WM_SIZE` | `view_.Layout()` | пересчитать раскладку |
| `WM_GETMINMAXINFO` | `view_.MinWidth/MinHeight()` | минимальный размер окна |
| `WM_ERASEBKGND` → `1` | фон рисуем сами | убирает мерцание |
| `WM_PAINT` | двойная буферизация + `view_.Paint` | плавное видео |
| `WM_TIMER` | `OnTimer(wp)` | 3 разных таймера по id |
| `WM_COMMAND` | `OnCommand(id, code)` | кнопки |
| `WM_HOTKEY` | `OnHotkey()` | `Ctrl+Shift+F12` |
| `WM_DEVICECHANGE` | `RefreshDevices(false)` | камеру подключили/отключили |
| `WM_STATE` (`WM_APP+1`) | `OnCameraState(state, text)` | состояние из потока |
| `WM_FRAME` (`WM_APP+2`) | `InvalidateRect` только предпросмотра | экономия перерисовки |
| `WM_TRAY` (`WM_APP+3`) | `OnTray(lp)` | клики по значку |
| `WM_DPICHANGED` | `SetDpi`, `RecreateFonts`, `Layout` | перенос окна на другой монитор |
| `WM_DRAWITEM` | `view_.DrawItem(item)` | owner-draw |
| `WM_CTLCOLOREDIT/LISTBOX` | тёмные цвета + кисть | поле каталога и журнал |
| `WM_CLOSE` → `DestroyWindow` | `Cleanup()` в `WM_DESTROY` | корректное завершение |
| `WM_DESTROY` | `Cleanup(); PostQuitMessage(0)` | выход из цикла сообщений |

Свои сообщения начинаются с `WM_APP`, а не с `WM_USER`: `WM_USER` может
использовать любой класс окна внутри приложения, `WM_APP` — только мы.

### 4.3. Три таймера

| id | Период | Роль |
|---|---|---|
| `TIMER_INFO` | 500 мс | обновить «Режим/Формат», состояние записи, доступность кнопок, перерисовать |
| `TIMER_CHORD` | 25 мс | опрос пары клавиш «-» + «=» |
| `TIMER_TOAST` | 80 мс | гашение всплывающих плашек (запускается по необходимости и сам останавливается) |

### 4.4. `OnCreate()` — порядок запуска

1. `view_.Create(...)` — контролы и шрифты;
2. заполнить список разрешений;
3. каталог по умолчанию + `EnsureDir`;
4. `camera_.SetNotifyWindow(hwnd_)` — куда поток шлёт `WM_STATE`;
5. `AddTrayIcon()` — значок в трее;
6. `RegisterHotKey(..., MOD_CONTROL|MOD_SHIFT, VK_F12)`;
7. два таймера;
8. `AddLog("Приложение запущено")`, `RefreshDevices(true)`, `Layout`, `UpdateModel`.

### 4.5. `OnCommand()` — что делает каждая кнопка

| ID | Действие |
|---|---|
| `ID_CONNECT` / `ID_DISCONNECT` | `Connect()` / `Disconnect()` |
| `ID_REFRESH` | перечитать список камер |
| `ID_SNAPSHOT` | `TakeSnapshot(false)` — снимок из окна |
| `ID_RECORD_START` / `ID_RECORD_STOP` | `StartRecording()` / `StopRecording()` |
| `ID_BROWSE` | `SHBrowseForFolderW` → каталог |
| `ID_REPORT` | `SaveReport()` |
| `ID_TRAY_BUTTON` | `HideToTray()` |
| `ID_MENU_*` | пункты меню значка в трее |

## 5. Снимок, отчёт, каталог

### `TakeSnapshot(background)`

```
ApplyDirectory()                 // прочитать поле каталога, создать при необходимости
├─ Latest(frame)                // есть готовый кадр?
├─ нет → WaitForFrame(1500 мс)  // только что подключили — ждём первый кадр
├─ нет → причина по состоянию: не подключена / не успела выдать / недоступна
│         → AddLog + Notify, выход
├─ SnapshotPath(save_dir_)      // snapshot_20261106_121552.jpg (+ _1 при совпадении)
├─ cv::Mat обёртка над Frame.bgr (без копирования!)
├─ ImwriteAny(path, mat, 92)    // JPEG q=92
└─ ++snapshot_count_, last_snapshot_ = имя
   AddLog(...) + Notify("Снимок сохранён: ...")
```

Важная деталь: `Mat mat(h, w, CV_8UC3, frame.bgr.data())` — конструктор-обёртка,
данные не копируются, а `Frame` живёт до конца функции.

`background` = `true` значит «снимок сделан не из окна» (горячая клавиша) —
влияет на уровень записи в журнале и текст уведомления.

### `SaveReport()`

Пишет `report_YYYYMMDD_HHMMSS.txt`: заголовок, дата, и весь журнал построчно.
Кодировка UTF-8 **с BOM** — иначе Блокнот покажет кириллицу кракозябрами.

### `ApplyDirectory()`

Берёт текст из `EDIT`. Если каталог создать нельзя — откатывается на
`DefaultSaveDir()` и сообщает плашкой (в журнал не пишет — не значимое событие).

## 6. Скрытый режим: трей и горячие клавиши

### `AddTrayIcon()` / `HideToTray()` / `Restore()` / `OnTray()`

```cpp
NOTIFYICONDATAW data{};
data.hWnd = hwnd_;
data.uFlags = NIF_ICON | NIF_MESSAGE | NIF_TIP;
data.uCallbackMessage = WM_TRAY;            // куда придёт клик
Shell_NotifyIconW(NIM_ADD, &data);
```

`WM_TRAY` приходит в `lParam` с кодом мыши: `LOWORD(lp) == WM_LBUTTONDBLCLK`
→ `Restore()` (показать, поднять, `SetForegroundWindow`), `WM_RBUTTONUP` →
`TrackPopupMenu` с «Показать окно / Сделать снимок / Выход».

`HideToTray()` перед скрытием **сам подключает камеру**, если она не
подключена: иначе фоновый снимок невозможен.

### Два способа снимка

| Комбинация | Механизм | Почему так |
|---|---|---|
| `Ctrl+Shift+F12` | `RegisterHotKey` → `WM_HOTKEY` → `OnHotkey()` | штатный системный способ, работает при любом фокусе |
| `-` + `=` одновременно | `GetAsyncKeyState` каждые 25 мс → `PollChord()` | `RegisterHotKey` не умеет регистрировать пару обычных клавиш, только одну клавишу + модификаторы |

`PollChord()` смотрит старший бит состояния клавиши (`0x8000` — нажата сейчас)
и срабатывает **по фронту**: `both && !chord_down_` — одно нажатие даёт один
снимок, удержание не «строчит».

### `Notify()` — единая точка уведомлений

```cpp
if (hidden_) Balloon(...);        // окно скрыто → balloon tip у значка
else         view_.PushToast(...); // окно видно → плашка в окне
```

Так пользователь всегда видит результат: в скрытом режиме — системное
уведомление, в открытом — короткая плашка (2,6 с, до трёх сразу).

## 7. Журнал

`AddLog(level, text)` делает три вещи:

1. хранит строку в `log_` (для отчёта, максимум 2000 — старые вытесняются);
2. добавляет её в `LISTBOX` окна (`view_.AddLogLine`) — тот owner-draw, поэтому
   строки цветные по уровню;
3. **дописывает в `camera_log.txt`** (UTF-8 + BOM, `FILE_APPEND_DATA`): журнал
   не теряется даже при аварийном завершении.

Уровни: `0` — обычное, `1` — предупреждение, `2` — ошибка, `3` — успех
(снимок/запись в фоне).

Что пишется: запуск, подключение/отключение и ошибки камеры, снимки, начало и
остановка записи, нажатие горячей клавиши в скрытом режиме, закрытие.
Остальное (список камер, старт записи, выбор каталога) — плашками.

## 8. Точка входа `wWinMain`

1. **DPI**: `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` через
   `GetProcAddress` (функция есть не везде) с запасным `SetProcessDPIAware()`;
   затем `SetDpi(GetDeviceCaps(LOGPIXELSY))`.
2. **GDI+**: `GdiplusStartup` — без него не работают `Graphics`, `Font`, `Path`.
3. **COM**: `CoInitializeEx(COINIT_APARTMENTTHREADED)` — нужен DirectShow
   (перечисление камер) и `SHBrowseForFolderW`. Парная `CoUninitialize`.
4. **Common Controls v6** + манифест в `#pragma comment(linker, ...)` —
   современный вид системных элементов.
5. `App app; app.Init(...); app.Run();` — цикл `GetMessage/TranslateMessage/DispatchMessage`.
6. В конце — `GdiplusShutdown`.

## 9. `visual.cpp` — визуальная часть

### 9.1. Тема и DPI

Все размеры записаны в **DIP** (независимые от DPI пиксели, как в Android/WPF):

```cpp
int S(int dip) { return MulDiv(dip, g_dpi, 96); }   // 96 DPI — базовый
```

При 125 % `S(24)` = 30 px, при 150 % = 36 px. И шрифты, и координаты считаются
через `S()`, поэтому окно на любом масштабе выглядит одинаково, а не «мелко и
мыльно». При `WM_DPICHANGED` шрифты пересоздаются (`RecreateFonts`).

### 9.2. Помощники рисования

| Функция | Роль |
|---|---|
| `FillRectG` | прямоугольник `SolidBrush`. Отдельная функция, потому что перегрузки `Graphics::FillRectangle` неоднозначны (INT vs REAL) |
| `RoundedRect` | скруглённая плашка через `GraphicsPath`: 4 дуги + `FillPath` + `DrawPath` |
| `Card` | плашка карточки (полупрозрачный фон + рамка) |
| `TextG` | текст с обрезкой `EllipsisCharacter` и `NoWrap` — длинный путь каталога не вылезет за карточку |
| `TextWidth` | измерение текста (`MeasureString`) — для ширины статуса и плашек |
| `Row` | строка «подпись — значение» фиксированной высоты |
| `Dot`, `Separator` | индикатор состояния, разделитель |

### 9.3. `View::Layout()` — раскладка «потоком»

Каждая карточка считается отдельно, элементы ставятся **под предыдущим**
(переменная `y` растёт), а не по абсолютным координатам от верха и низа окна.
Поэтому надписи не наезжают друг на друга.

Если места мало (маленькое окно или большой DPI), адаптивно убираются:
сначала подсказка, потом «Последний снимок», потом лишние строки сведений.
Каждая карточка ещё и обрезается при рисовании (`SetClip` по её прямоугольнику) —
физически не может вылезти на соседнюю.

`MinWidth/MinHeight` считают минимальный размер окна так, чтобы обязательные
элементы точно помещались (`WM_GETMINMAXINFO`).

### 9.4. `View::Paint()`

Порядок: фон → шапка → предпросмотр → панель камеры → карточка сохранения →
журнал → плашки уведомлений. Каждый `Draw*` ставит свой клип и снимает его
(`ResetClip`).

### 9.5. Видео в предпросмотре — `DrawPreview`

```cpp
BITMAPINFO bmi{};  bmi.bmiHeader.biHeight = -height;   // минус = строки сверху вниз
SetStretchBltMode(vdc, HALFTONE);
StretchDIBits(vdc, x, y, w, h, 0, 0, width, height, frame.bgr, &bmi, DIB_RGB_COLORS, SRCCOPY);
```

GDI+ не умеет рисовать BGR24 напрямую, поэтому кадр выводится GDI через
`GetHDC()/ReleaseHDC()` того же `Graphics`. `HALFTONE` — сглаженное
масштабирование, отрицательная высота — чтобы изображение не было перевёрнуто
(в DIB по умолчанию строки идут снизу вверх). Пропорции сохраняются: считается
`scale` как минимум из отношений сторон, кадр центрируется.

### 9.6. Owner-draw

`View::DrawItem()` — одна точка входа для трёх типов:

- `DrawButton` — плашка + текст; **три состояния**: обычная, нажатая
  (`ODS_SELECTED`), отключённая (`ODS_DISABLED` — светлый серый текст, читаемый
  на тёмном фоне); «Подключить» и «Снимок» — зелёные (главные действия);
- `DrawCombo` — `itemID == -1` значит «поле выбора», рисуем рамку, текущий
  текст и стрелку; иначе — пункт выпадающего списка;
- `DrawLogItem` — время серым, сообщение цветом уровня; ширину колонки времени
  считает `TextWidth`, поэтому текст не прилипает к дате.

Почему owner-draw: стандартные кнопки и списки рисуются системным светлым
стилем, перекрасить их полностью нельзя — только нарисовать самому
(`BS_OWNERDRAW` / `CBS_OWNERDRAWFIXED` / `LBS_OWNERDRAWFIXED`).

### 9.7. `PushToast` / `ExpireToasts` / `DrawToasts`

Уведомления — вектор `Toast{текст, уровень, время окончания}`. Новые
добавляются в конец, при количестве > 3 старые удаляются. `ExpireToasts()`
выбрасывает просроченные и возвращает «есть ли ещё» — по этому ответу окно
останавливает таймер. В последние 400 мс альфа падает до 0 — плавное затухание.

## 10. Многопоточность: главный вопрос на защите

**Что защищено и чем:**

| Данные | Кто пишет | Кто читает | Защита |
|---|---|---|---|
| `latest_` (кадр) | поток захвата | GUI (`Latest`, `WaitForFrame`) | `mutex_` + `condition_variable` |
| `format_` | поток захвата | GUI (`FormatName`) | тот же `mutex_` |
| `state_` | оба | GUI | `std::atomic<CamState>` |
| `measured_fps_` | поток | GUI | `std::atomic<double>` |
| `running_` | GUI | поток | `std::atomic<bool>` |
| `record_start_/stop_` | GUI | поток | `atomic` + `record_mutex_` |
| `record_state_` | поток | GUI | `std::atomic<int>` |
| `writer_` | **только поток** | — | владение одним потоком |
| GUI, `log_`, `devices_` | только GUI-поток | — | однопоточный доступ |

**Правила, которые стоит назвать вслух:**

1. Поток захвата **не вызывает** функции GUI и не трогает `HWND`-контролы —
   только `PostMessage`.
2. `Notify()` создаёт `new std::wstring` и передаёт владение окну через
   `LPARAM`; если `PostMessage` не удался — сам её удаляет (нет утечки).
3. `Stop()` всегда `join()`-ит поток до освобождения ресурсов — никаких
   «осиротевших» потоков при выходе.
4. `WaitForFrame` будится `frame_cv_.notify_all()` сразу после публикации кадра.

**Почему нет мьютекса вокруг `writer_`:** им владеет только поток захвата,
GUI передаёт лишь «намерение» (путь + флаг).

## 11. Сквозные сценарии (рассказать по шагам)

### Снимок кнопкой
`WM_COMMAND(ID_SNAPSHOT)` → `TakeSnapshot(false)` → `Latest/WaitForFrame` →
`SnapshotPath` → `ImwriteAny` → `AddLog` + `Notify` (плашка) → `InvalidateRect`.

### Снимок в скрытом режиме
окно скрыто (`ShowWindow(SW_HIDE)`, камера работает) → пользователь жмёт
`-`+`=` в любом приложении → таймер 25 мс замечает обе клавиши → фронт →
`TakeSnapshot(true)` → файл `snapshot_….jpg` → `Notify` видит `hidden_` →
**balloon tip** у значка → строка в журнал.

### Запись видео
`ID_RECORD_START` → `StartRecording()` → `Camera::StartRecording` (путь + флаг,
`Pending`) → поток захвата открывает `VideoWriter` → `RecordOn` → следующий
`WM_TIMER` вызывает `SyncRecording()` → «Запись начата» в журнал и плашкой.
Остановка — флаг `stop`, поток делает `release()`, файл дописан корректно.

### Отключение камеры на ходу
`WM_DEVICECHANGE` → `RefreshDevices` → список обновился. Если отключили во время
захвата — 30 пустых кадров → поток выходит → `Notify(Failed, "Камера перестала
отдавать кадры…")` → красный индикатор, кнопка «Подключить» снова активна.

### Выход
`WM_CLOSE` → `DestroyWindow` → `WM_DESTROY` → `Cleanup()`: остановить таймеры,
снять `UnregisterHotKey`, `camera_.Stop()` (join + закрыть AVI), удалить значок
(`NIM_DELETE`), `AddLog("Приложение закрыто")`, `PostQuitMessage`.

## 12. Вероятные вопросы и короткие ответы

1. **Где хранится кадр и почему копия?** В `Camera::latest_` под мьютексом;
   копия — потому что `cv::Mat` переиспользует буфер, указатель стал бы висячим.
2. **Почему поток, а не таймер?** `read()` блокирующий (до десятков мс); в
   GUI-потоке он «замораживал» бы окно и перетаскивание.
3. **Как поток сообщает о новом кадре?** `PostMessage(WM_APP+2)`; не
   `SendMessage`, чтобы не ждать отрисовку.
4. **Почему `WM_APP`, а не `WM_USER`?** `WM_USER` может использоваться внутри
   любого класса окна; `WM_APP` зарезервирован за приложением.
5. **Как сделан снимок в фоне без окна?** Камера работает в потоке, окно
   скрыто; снимок берёт `latest_` — окно для этого не нужно.
6. **Что будет, если камеру выдернуть?** 30 пустых кадров → поток выходит →
   состояние `Failed`, индикатор красный, в журнал ошибка.
7. **Почему `RegisterHotKey` не может `-`+`=`?** Регистрируется одна клавиша +
   модификаторы (`Ctrl/Alt/Shift/Win`); две обычные клавиши — нельзя, поэтому
   опрос `GetAsyncKeyState`.
8. **Как избежать «строчки» снимков при удержании?** Детекция фронта:
   `both && !chord_down_`.
9. **Что такое owner-draw?** Рисование контрола приложением по сообщению
   `WM_DRAWITEM` вместо системы (`BS_OWNERDRAW` и т.п.).
10. **Зачем двойная буферизация?** Рисование в `CreateCompatibleBitmap` и один
    `BitBlt` — иначе на 30 к/с видно мерцание.
11. **Почему видео выводится GDI, а не GDI+?** GDI+ не принимает BGR24;
    `StretchDIBits` умеет напрямую и с `HALFTONE` масштабирует сглаженно.
12. **Почему `biHeight` отрицательный?** DIB по умолчанию хранит строки снизу
    вверх; минус переключает на порядок сверху вниз, как у камеры.
13. **Что такое DIP и `S()`?** Дизайнерские пиксели при 96 DPI; `MulDiv(dip,
    dpi, 96)` переводит их в физические — шрифты и отступы масштабируются.
14. **Зачем `WM_DPICHANGED`?** Перенесли окно на монитор с другим масштабом —
    пересоздать шрифты и раскладку, иначе текст поедет.
15. **Как не теряется журнал?** Каждая строка сразу дописывается в
    `camera_log.txt` (UTF-8+BOM), плюс копия в памяти для отчёта.
16. **Зачем BOM в UTF-8?** Чтобы Блокнот/Word определили кодировку.
17. **Почему `CoInitializeEx` обязателен?** DirectShow и `SHBrowseForFolderW` —
    COM-компоненты; без инициализации COM вернёт ошибку.
18. **Где освобождаются ресурсы?** `Release()` у COM-интерфейсов, `DeleteObject`
    у кистей, `delete` у шрифтов (`View::Destroy`), `join()` у потока, `NIM_DELETE`
    у значка — всё в `Cleanup()`/деструкторах.
19. **Кто закрывает AVI при выходе?** `Camera::Stop()` → `join()` → `release()`;
    поток успевает дописать файл, потому что цикл завершается по `running_`.
20. **Почему путь к файлу конвертируется дважды (UTF-8/ANSI)?** OpenCV на
    Windows не всегда открывает путь с кириллицей по UTF-8; вторая попытка в
    системной кодировке — практическая страховка.
21. **Почему индекс камеры из DirectShow подходит для OpenCV?** OpenCV с
    бэкендом DSHOW перечисляет устройства тем же перечислителем в том же
    порядке.
22. **Что будет при двух снимках в одну секунду?** `SnapshotPath` добавит
    `_1`, `_2` — файлы не перезапишут друг друга.
23. **Почему `bs`-стили, а не `WS_EX_CLIENTEDGE`?** Внешняя рамка давала двойную
    обводку поверх собственной скруглённой рамки карточки.
24. **Где логика, а где визуал?** Логика в `App`/`Camera` (main.cpp), визуал в
    `View` (visual.cpp); обмен — только структура `Model` и вызовы `View`.
25. **Что было бы с OpenCV-окнами (`cv::imshow`)?** Нельзя: GUI обязан быть
    Win32 по заданию, плюс `imshow` создаёт своё окно со своим циклом сообщений
    и конфликтует с нашим.

## 14. Слабые места — знать заранее

1. **Разрешения — фиксированный список**, а не реальные возможности камеры.
   Строго по заданию (п. 3) нужен `IAMStreamConfig::GetStreamCapabilities`:
   `GetNumberOfCapabilities` → `GetStreamCaps` → список режимов из драйвера.
   Честный ответ: «список запрашиваемых режимов; фактический — показывается
   в сведениях после подключения; расширение через IAMStreamConfig возможно,
   интерфейс описан в теории».
2. **OpenCV запрещён целью работы.** Ответ: перечисление устройств, трей,
   горячие клавиши, журнал, файловые пути и весь GUI — чистый Win32 API;
   OpenCV применён только как декодер кадров и кодек JPEG/MJPEG, по
   согласованию с преподавателем.
3. **Уведомления в окне — не «balloon tip»** из задания. Ответ: в скрытом
   режиме используется именно `Shell_NotifyIcon(NIM_MODIFY, NIF_INFO)`, как
   требует задание; плашки в окне — дополнительное удобство, когда окно видно.
4. **Частота кадров не выбирается** — фиксированные 30 к/с. Ответ: лишняя
   настройка убрана по требованию, фактический FPS виден в сведениях.
