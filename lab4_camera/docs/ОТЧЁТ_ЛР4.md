## 1. Цель работы

Изучить архитектуру подсистем видеозахвата ОС Windows, освоить программные
интерфейсы обнаружения, идентификации и управления веб-камерами; получить

сохранения видеопотока в реальном времени с использованием низкоуровневых
системных API (DirectShow / Media Foundation) и научиться реализовывать
фоновый режим наблюдения, журналирование событий и управление горячими
клавишами.

## 2. Задание

Реализовать приложение с возможностью фонового создания снимков:

1. главное окно приложения со всеми элементами базового монитора;
2. кнопка «Свернуть в трей» — скрытие окна, оставление иконки в системном трее
   (`Shell_NotifyIcon`);
3. глобальная горячая клавиша для создания снимка без отображения окна —
   в работе это одновременное нажатие `-` и `=`
   (резервная комбинация `Ctrl+Shift+F12` через `RegisterHotKey`);
4. при нажатии горячей клавиши в фоновом режиме — захват кадра с камеры и
   сохранение в выбранный каталог с именем `snapshot_YYYYMMDD_HHMMSS.jpg`;
5. уведомление об успешном сохранении снимка — плашка в окне, а при скрытом
   окне balloon tip у значка в трее;
6. восстановление главного окна по двойному клику на иконке в трее;
7. журналирование фоновых операций.

Дополнительно (функционал базового монитора): предпросмотр в реальном времени,
выбор камеры и разрешения, кнопки **«Начать запись» / «Остановить запись»**
(`cv::VideoWriter`, MJPG/AVI), каталог сохранения, индикатор состояния камеры,
журнал и выгрузка отчёта.

## 4. Архитектура приложения

Приложение разделено на два модуля (~1900 строк вместе):

* **`main.cpp` — логика.** Утилиты (строки, время, файлы) → перечисление камер
  и поток захвата `Camera` → класс `App`: сообщения окна, снимки, журнал,
  отчёт, трей, горячая клавиша. Про интерфейс знает только через `visual::View`.
* **`visual.cpp` — визуал.** Палитра `namespace theme`, масштаб `S()` по DPI,
  шрифты, раскладка `View::Layout()` и отрисовка `View::Paint()`, owner-draw
  кнопок, списков и журнала. Про камеру и файлы не знает ничего: получает
  готовую структуру `visual::Model` (состояние, тексты, кадр для предпросмотра).

`visual.h` — тонкий интерфейс между ними: `Model`, идентификаторы контролов и
объявления методов `View`. Такое разделение позволяет менять оформление,
не трогая логику, и наоборот.

```
              ┌───────────────────────────────────────────────┐
              │            Главное окно (Win32)               │
              │ шапка: индикатор состояния камеры и счётчик   │
              │ ┌───────────────────┐ ┌─────────────────────┐ │
              │ │  предпросмотр     │ │ панель устройства   │ │
              │ │  (StretchDIBits)  │ │ (камера, режим,    │ │
              │ └───────────────────┘ │  инфо, кнопки)     │ │
              │ ┌───────────────────┐ └─────────────────────┘ │
              │ │ панель сохранения │ ┌─────────────────────┐ │
              │ │ (каталог, кнопки) │ │  журнал событий     │ │
              │ └───────────────────┘ └─────────────────────┘ │
              └──────┬───────────────────────────┬────────────┘
                     │ WM_STATE / WM_FRAME       │ WM_HOTKEY, WM_TRAY
                     ▼                           │ WM_DEVICECHANGE
              ┌──────────────────────────┐       │
              │  Camera (поток захвата)  │       │
              │  cv::VideoCapture        │       │
              │  последний кадр + FPS    │       │
              └──────┬───────────────────┘       │
                     │ последний кадр (копия)    │
                     ▼                           ▼
              ┌──────────────────────────┐  ┌──────────────────┐
              │  TakeSnapshot()          │  │  Значок в трее,  │
              │  cv::imwrite -> JPEG     │  │  горячая клавиша │
              └──────────────────────────┘  └──────────────────┘
```

Ключевые решения:

* **GUI-поток не вызывает камеру напрямую.** Поток захвата кладёт кадр в
  `latest_` под мьютексом и посылает окну `WM_STATE`/`WM_FRAME`; окно берёт
  копию кадра при отрисовке. Блокирующее чтение кадра не «морозит» интерфейс.
* **Двойная буферизация отрисовки** (рисование в `CreateCompatibleBitmap` с
  последующим `BitBlt`) — иначе окно мерцает на 30 кадрах в секунду.
* **Снимок ждёт кадр, а не падает сразу.** `Camera::WaitForFrame()` держит
  ожидание до 1,5 с (условная переменная, будится потоком захвата), поэтому
  снимок сразу после «Подключить», пока камера разгоняется, не завершается
  ложной ошибкой. Если кадра нет, причина пишется в журнал по состоянию
  камеры: «камера не подключена» / «камера не успела выдать кадр» /
  «камера недоступна».
* **Снимок берётся из последнего кадра**, а не открытием камеры заново —
  поэтому нажатие горячей клавиши в скрытом режиме срабатывает мгновенно.
* **Раскладка считается «потоком»** в `View::Layout()`: каждый блок ставится
  под предыдущим в пределах своей карточки, содержимое обрезается по её
  границам, а необязательные блоки (подсказка, «последний снимок», лишние
  строки) убираются, когда места не хватает. Поэтому надписи не накладываются
  друг на друга при любом размере окна, в том числе в оконном режиме, и при
  любом масштабе DPI.
* **Состояние камеры** (`Off / Opening / On / Failed`) передаётся в GUI
  сообщением `WM_STATE` и отображается цветным индикатором в шапке.

## 5. Реализация по пунктам задания

### 5.1. Обнаружение устройств и информация о них

Перечисление выполняется через DirectShow — это тот же механизм, которым
пользуется OpenCV с бэкендом DSHOW, поэтому индексы устройств совпадают:

```cpp
ICreateDevEnum* dev_enum = nullptr;
CoCreateInstance(CLSID_SystemDeviceEnum, nullptr, CLSCTX_INPROC_SERVER,
                 IID_PPV_ARGS(&dev_enum));
IEnumMoniker* enum_moniker = nullptr;
dev_enum->CreateClassEnumerator(CLSID_VideoInputDeviceCategory, &enum_moniker, 0);

IMoniker* moniker = nullptr;
while (enum_moniker->Next(1, &moniker, nullptr) == S_OK) {
    IPropertyBag* bag = nullptr;
    moniker->BindToStorage(nullptr, nullptr, IID_PPV_ARGS(&bag));
    VARIANT value; VariantInit(&value);
    bag->Read(L"FriendlyName", &value, nullptr);   // «USB2.0 HD UVC WebCam»
    ...
}
```

`cv::VideoCapture` на Windows не отдаёт имя камеры, поэтому список в интерфейсе
строится по данным DirectShow.

Текущий режим читается у открытого устройства:

```cpp
capture.set(cv::CAP_PROP_FOURCC, cv::VideoWriter::fourcc('M','J','P','G'));
capture.set(cv::CAP_PROP_FRAME_WIDTH, width);
capture.set(cv::CAP_PROP_FRAME_HEIGHT, height);
capture.set(cv::CAP_PROP_FPS, fps);
```

Фактические значения (`CAP_PROP_FRAME_WIDTH/HEIGHT/FOURCC/FPS`) выводятся в
панели «Информация» и обновляются раз в секунду.

### 5.2. Предпросмотр в реальном времени

```cpp
BITMAPINFO bmi{};
bmi.bmiHeader.biSize = sizeof(BITMAPINFOHEADER);
bmi.bmiHeader.biWidth = frame.width;
bmi.bmiHeader.biHeight = -frame.height;   // top-down
bmi.bmiHeader.biPlanes = 1;
bmi.bmiHeader.biBitCount = 24;
bmi.bmiHeader.biCompression = BI_RGB;

SetStretchBltMode(dc, HALFTONE);
StretchDIBits(dc, x, y, w, h, 0, 0, frame.width, frame.height,
              frame.bgr.data(), &bmi, DIB_RGB_COLORS, SRCCOPY);
```

Кадр хранится как BGR24 (`struct Frame`), пропорции сохраняются (letterbox), в
левом нижнем углу выводится дата и время.

### 5.3. Снимок кадра

```cpp
std::wstring UniquePath(dir, L"snapshot", L"jpg");
// snapshot_20261029_183012.jpg; если файл уже есть — snapshot_20261029_183012_1.jpg
```

Сохранение — `cv::imwrite` с качеством 92. Путь передаётся как UTF-8, при
неудаче — в системной ANSI-кодировке (это спасает каталоги с кириллицей):

```cpp
if (!cv::imwrite(ToUtf8(path), mat, params))
    cv::imwrite(ToAnsi(path), mat, params);
```

### 5.4. Скрытый режим: трей

```cpp
void App::HideToTray() {
    if (camera_.State() != CamState::On && !devices_.empty())
        Connect();                              // иначе фоновый снимок невозможен
    ShowWindow(hwnd_, SW_HIDE);
    hidden_ = true;
    AddLog(3, L"Окно свёрнуто в трей — работает фоновое фотонаблюдение");
    Balloon(L"Фотонаблюдение включено", L"«-» и «=» одновременно — снимок без окна", NIIF_INFO);
}
```

Значок добавляется один раз при запуске:

```cpp
NOTIFYICONDATAW data{};
data.cbSize = sizeof(data);
data.hWnd = hwnd_;  data.uID = 1;
data.uFlags = NIF_ICON | NIF_MESSAGE | NIF_TIP;
data.uCallbackMessage = WM_TRAY;
Shell_NotifyIconW(NIM_ADD, &data);
```

Обработка событий значка: `WM_LBUTTONDBLCLK` → `Restore()`,
`WM_RBUTTONUP` → контекстное меню (показать окно / снимок / выход).

### 5.5. Запись видео (функционал базового монитора)

Кнопки «Начать запись» / «Остановить запись» открывают и закрывают
`cv::VideoWriter`; файл пишется в том же каталоге, что и снимки:

```cpp
// в потоке захвата, сразу после получения очередного кадра
writer_.open(ToUtf8(path), cv::VideoWriter::fourcc('M', 'J', 'P', 'G'), fps,
             cv::Size(frame.cols, frame.rows));
...
if (writer_.isOpened()) writer_.write(frame);   // кадр BGR -> MJPG
```

Управление из GUI не трогает файл напрямую: `Camera::StartRecording()` только
кладёт путь и флаг под мьютекс, а открытие/закрытие и саму запись делает поток
захвата — так нет гонок за `VideoWriter`. Кнопки включаются по состоянию
(`Camera::Recording()`), запись автоматически прекращается при отключении
камеры и при выходе из приложения.

### 5.6. Уведомления в окне

Вместо потока системных balloon tip'ов уведомления рисуются плашками поверх
предпросмотра: до трёх одновременно, по 2,6 с, с плавным затуханием
(`View::PushToast()` / `View::DrawToasts()`). Перерисовку ведёт таймер 80 мс,
который останавливается, когда все плашки погасли. Если окно скрыто в трей —
используется обычный balloon tip (`App::Notify()` выбирает способ сам).

### 5.7. Глобальная горячая клавиша и снимок в фоне

Горячая клавиша — **одновременное нажатие `-` и `=`**. `RegisterHotKey` умеет
регистрировать только одну клавишу с модификаторами, поэтому пара обычных
клавиш отслеживается опросом их состояния (окно при этом может быть скрыто —
`GetAsyncKeyState` работает независимо от фокуса):

```cpp
const UINT kChordPollMs = 25;   // период опроса, мс

void App::PollChord() {
    const bool minus = (GetAsyncKeyState(VK_OEM_MINUS) & 0x8000) != 0;
    const bool plus  = (GetAsyncKeyState(VK_OEM_PLUS)  & 0x8000) != 0;
    const bool both  = minus && plus;

    if (both && !chord_down_) {       // фронт нажатия: один снимок на одно нажатие
        chord_down_ = true;
        TakeSnapshot(true);
    } else if (!both) {
        chord_down_ = false;
    }
}

// в App::OnCreate()
SetTimer(hwnd_, TIMER_CHORD, kChordPollMs, nullptr);
```

Резервная комбинация `Ctrl+Shift+F12` регистрируется обычным способом:

```cpp
alt_hotkey_ok_ = RegisterHotKey(hwnd_, HOTKEY_SNAPSHOT_ALT, MOD_CONTROL | MOD_SHIFT,
                                VK_F12) != FALSE;
```

Сворачивание в трей горячей клавиши не имеет: это кнопка «Свернуть в трей»
в шапке окна (`ID_TRAY_BUTTON` → `HideToTray()`), а вернуть окно можно двойным
щелчком по значку в трее (`WM_LBUTTONDBLCLK` → `Restore()`).

`TakeSnapshot(true)`:

1. берёт **последний** кадр из `Camera` (камера уже открыта — задержка
   минимальна, повторное открытие устройства не требуется); если кадра ещё нет,
   ждёт его до 1,5 с (`Camera::WaitForFrame()`);
2. сохраняет JPEG в выбранный каталог;
3. пишет в журнал строку о снимке;
4. показывает уведомление с именем файла — плашку в окне, а при скрытом окне
   balloon tip у значка в трее (`App::Notify()`).

Если сигнала нет — в журнал и в уведомление пишется причина («камера не
подключена» / «камера не успела выдать кадр» / «камера недоступна»);
приложение при этом не падает.

### 5.8. Журналирование

Журнал ведётся в `App::AddLog()`: запись добавляется в список окна
(`LBS_OWNERDRAWFIXED`, цвет зависит от уровня) и сразу дописывается в
`camera_log.txt` в каталоге сохранения (UTF-8 с BOM), поэтому он не теряется
даже при аварийном завершении. Кнопка «Сохранить отчёт» выгружает журнал в
`report_YYYYMMDD_HHMMSS.txt`.

Журнал намеренно короткий — только значимые события:

* запуск приложения;
* подключение камеры (в том числе неудачное) и отключение;
* снимки (успешные и неудачные, с причиной);
* выход из приложения.

Служебные сообщения (обновление списка камер, уведомления о записи, ошибки
каталога) показываются плашками в окне и журнал не засоряют.

Пример журнала:

```
29.10.2026 18:29:58.114  Приложение запущено
29.10.2026 18:30:02.771  Камера подключена: 1280 × 720
29.10.2026 18:30:25.612  Снимок сохранён: snapshot_20261029_183025.jpg (1280 × 720, 148.3 КБ)
29.10.2026 18:31:40.208  Снимок сохранён: snapshot_20261029_183140.jpg (1280 × 720, 151.7 КБ)
29.10.2026 18:35:12.900  Камера отключена
29.10.2026 18:35:20.004  Приложение закрыто
```

### 5.9. Контроль состояния камеры

* окно обрабатывает `WM_DEVICECHANGE` (`DBT_DEVNODES_CHANGED`,
  `DBT_DEVICEARRIVAL`, `DBT_DEVICEREMOVECOMPLETE`) и сразу перечитывает список
  камер — подключённая камера появляется в списке без перезапуска;
* если кадры перестают приходить (камеру выдернули), поток захвата после 30
  неудачных попыток завершает работу и сообщает окну `CamState::Failed` —
  индикатор становится красным, в журнал пишется ошибка, кнопка
  «Подключить камеру» снова активна.

### 5.10. Интерфейс

Главное окно (Win32, без MFC/Qt) оформлено в том же стиле, что ЛР №1:

* всё рисуется через GDI+ (`Graphics`, сглаживание, ClearType) с двойной
  буферизацией — мерцания нет даже при 30 кадрах в секунду;
* фон — тёмная заливка с очень мягким вертикальным градиентом, без картинки;
* информация сгруппирована в полупрозрачные карточки `Card(215,18,26,44)`
  с рамкой `Line(70,95,135)` и скруглением 6 px;
* палитра из `theme.h` ЛР1: `Txt`, `Sub`, `Dim`, состояния `Good/Warn/Bad`;
* шрифты: один Segoe UI на всё приложение (24 bold — заголовок окна,
  16 bold — заголовки карточек, 14 — строки, кнопки и журнал), без смешивания
  гарнитур;

Состав окна: заголовок с индикатором состояния камеры, кнопка «Свернуть в трей»; карточка «Предпросмотр» (видео с сохранением
пропорций); карточка «Камера» (устройство, разрешение, кнопки
подключения, строки «Режим / Формат / Снимков», имя последнего файла
и подсказка про скрытый режим); карточка «Фотонаблюдение» (каталог, «Снимок»,
«Сохранить отчёт»); карточка «Журнал событий».

Размеры шрифтов и раскладки заданы в DIP и умножаются на масштаб DPI, процесс
объявлен per-monitor DPI aware, при `WM_DPICHANGED` шрифты пересоздаются —
на 125/150 % текст остаётся чётким (в ЛР1, где размеры заданы в пикселях,
такого пересчёта нет).

Кнопки и выпадающие списки — owner-draw, поэтому тоже тёмные: `DrawButton()`
и `DrawCombo()` рисуют их теми же цветами, что и карточки.

Сознательно не добавлял лишнего: нет кнопок «Открыть каталог» и «Очистить
журнал», переключателя тем, второго бэкенда захвата и сохранения настроек в
реестр — остался ровно набор «базовый монитор + скрытый режим».

Журнал намеренно короткий: пишутся только запуск приложения, подключение и
отключение камеры (включая ошибки), снимки и выход. Служебные сообщения —
смена списка камер, переключение режима, старт/стоп записи — показываются
плашками в окне, но журнал не засоряют.

## 7. Выводы

В ходе работы изучены подсистемы видеозахвата Windows (DirectShow и Media
Foundation) и механизмы перечисления устройств (`ICreateDevEnum`,
`IEnumMoniker`, `IPropertyBag`). Разработано приложение на C++/Win32, которое
захватывает видеопоток, отображает его в реальном времени, сохраняет снимки
(JPEG), ведёт журнал с временными метками и умеет работать в скрытом режиме: окно сворачивается в трей, глобальная горячая
пара клавиш `-` + `=`, состояние которых опрашивается через `GetAsyncKeyState`, создаёт
снимок без открытия окна, результат подтверждается всплывающим уведомлением
`Shell_NotifyIcon(NIF_INFO)`.

Основные технические выводы:

* захват необходимо выполнять в отдельном потоке, а GUI уведомлять
  сообщениями (`PostMessage`), иначе блокирующее чтение кадра «подвешивает»
  интерфейс;
* кадр удобно хранить в BGR24 — этот формат одинаково понимают GDI
  (`StretchDIBits` с 24 битами на пиксель) и OpenCV (`cv::Mat`, `imwrite`,
  `VideoWriter`);
* для фонового режима камеру нельзя закрывать при скрытии окна — иначе
  теряется смысл «мгновенного» снимка по горячей клавише;
* `RegisterHotKey` надёжнее низкоуровневого хука клавиатуры: не требует
  отдельного потока с циклом сообщений и не вызывает подозрений у антивирусов;
* перечисление устройств через DirectShow (`ICreateDevEnum`) не открывает поток,
  поэтому безопасно при активном захвате (в отличие от повторного
  `cv::VideoCapture::open`, который может занять устройство).

## 8. Ответы на контрольные вопросы

**1. Подсистемы видеозахвата в Windows, их отличия.**
DirectShow — фильтровая архитектура (Filter Graph): источники, трансформации,
рендереры, граф собирается через `ICaptureGraphBuilder2`. Media Foundation —
более современный API (с Vista/7), конвейерная модель (Source Reader →
Transform → Sink Writer), лучше поддерживает аппаратное ускорение и
кодирование (H.264/AAC), рекомендован Microsoft для новых приложений.
DirectShow проще для legacy-устройств, MF — для записи/кодирования и
современного оборудования.

**2. Перечисление устройств через `CLSID_SystemDeviceEnum`.**
`CoCreateInstance(CLSID_SystemDeviceEnum, …)` создаёт `ICreateDevEnum`;
`CreateClassEnumerator(CLSID_VideoInputDeviceCategory, &pEnum, 0)` даёт
`IEnumMoniker` для категории «устройства видеозахвата»; `IEnumMoniker::Next`
возвращает `IMoniker` каждого устройства — это именованный объект COM,
представляющий устройство. `IMoniker::BindToStorage(…, IID_IPropertyBag, …)`
даёт свойства (`FriendlyName`, `DevicePath`), `IMoniker::BindToObject` —
сам фильтр-источник. Все интерфейсы освобождаются `Release()`.

**3. Список разрешений, FPS и форматов.**
DirectShow: `ICaptureGraphBuilder2::FindInterface` → `IAMStreamConfig`;
`GetNumberOfCapabilities`, затем `GetStreamCaps(i, &pmt, &caps)` —
`caps.InputSize` (разрешение), `caps.MinFrameInterval/MaxFrameInterval`
(100-нс интервалы), `pmt->subtype` (RGB24, MJPG, YUY2). Media Foundation:
`IMFMediaSource::CreatePresentationDescriptor` → `IMFStreamDescriptor` →
`IMFMediaTypeHandler`; `GetMediaTypeCount` и `GetMediaTypeByIndex`, далее
`MFGetAttributeSize(MF_MT_FRAME_SIZE)`, `MFGetAttributeRatio(MF_MT_FRAME_RATE)`,
`GetGUID(MF_MT_SUBTYPE)`.

**4. Форматы пикселей.**
RGB24 — 3 байта/пиксель, прост в обработке, но большой трафик.
YUY2 — 2 байта/пиксель (4:2:2), требует конвертации в RGB для отображения.
NV12 — 1.5 байта/пиксель (4:2:0), типичен для H.264-конвейеров.
MJPEG — сжатый кадр (обычно 5–15 % от RAW), максимальное разрешение при
ограниченной пропускной способности USB, но декодирование всё равно нужно.
Для 1280×720: RGB24 ≈ 2.7 МБ/кадр, YUY2 ≈ 1.8 МБ, NV12 ≈ 1.4 МБ;
MJPEG-кадр — сотни килобайт.

**5. Захват отдельного кадра.**
DirectShow — Sample Grabber (`ISampleGrabber::SetBufferSamples`,
`SetCallback`), буфер копируется в `GetBuffer`. Media Foundation —
`IMFSourceReader::ReadSample(…, &pSample)`, затем `ConvertToContiguousBuffer`
и `Lock` для доступа к RAW-данным. В работе захват идёт через
`cv::VideoCapture::read` (бэкенд DirectShow), который внутри повторяет ту же
схему: получить сэмпл → забрать буфер → скопировать пиксели в кадр BGR24.

**6. Сохранение кадра в BMP/JPEG без сторонних библиотек.**
BMP: сформировать `BITMAPFILEHEADER` (`"BM"`, смещение данных) и
`BITMAPINFOHEADER` (24 бита, `BI_RGB`), затем построчно записать BGR снизу
вверх с выравниванием строки до 4 байт. JPEG «вручную» — это реализация
DCT-кодировщика (нецелесообразно); поэтому в работе снимок пишется через
OpenCV (`cv::imwrite`), а BMP при необходимости формируется тем же способом,
что описан выше, — своим кодом без сторонних библиотек.

**7. Запись видео через `IMFSinkWriter`.**
`MFCreateSinkWriterFromURL(L"out.mp4", …)`; для видео-потока создать
выходной тип (`MF_MT_MAJOR_TYPE = MFMediaType_Video`,
`MF_MT_SUBTYPE = MFVideoFormat_H264`, размер, FPS, битрейт) и добавить поток
(`AddStream`); задать входной тип (`SetInputMediaType`); вызывать
`WriteSample` с `IMFSample` (метка времени `MFSampleExtension_*`,
`SetSampleDuration`); в конце — `Finalize`.

**8. Отслеживание подключения/отключения камеры.**
`RegisterDeviceNotification` с `DEV_BROADCAST_DEVICEINTERFACE`
(`GUID_DEVINTERFACE_IMAGE`) регистрирует окно на уведомления; система посылает
`WM_DEVICECHANGE` с `wParam = DBT_DEVICEARRIVAL` / `DBT_DEVICEREMOVECOMPLETE` /
`DBT_DEVNODES_CHANGED`. В обработчике перечисляется список устройств и
обновляется интерфейс; `UnregisterDeviceNotification` — при завершении.

**9. Скрытый режим, трей и горячие клавиши.**
Скрытый режим — приложение продолжает работать без видимого окна:
`ShowWindow(hwnd, SW_HIDE)` + значок `Shell_NotifyIcon(NIM_ADD)` с
`uCallbackMessage`, контекстным меню и balloon tip. Глобальная клавиша —
`RegisterHotKey(hwnd, id, MOD_CONTROL|MOD_SHIFT, VK_F12)`, событие приходит
как `WM_HOTKEY` с идентификатором в `wParam`; снимается
`UnregisterHotKey`. Окно при этом обязано обрабатывать сообщения (что и делает
цикл `GetMessage/DispatchMessage`).

**10. Привилегии и разрешения.**
Специальных прав администратора не нужно, но с Windows 10 доступ к камере
управляется параметром конфиденциальности («Параметры → Конфиденциальность →
Камера»): пользователь разрешает доступ приложениям и классическим
Win32-программам. Это защита приватности: камера — чувствительное устройство,
и ОС не позволяет приложениям снимать видео без ведома пользователя. При
отказе в доступе `open`/`ActivateObject` завершается ошибкой, которую
приложение показывает в журнале.

**11. Video4Linux2 и системные вызовы.**
V4L2 — драйверный интерфейс ядра Linux для устройств видео. Взаимодействие:
`open("/dev/videoN")`, настройка через `ioctl` (`VIDIOC_QUERYCAP`,
`VIDIOC_S_FMT`, `VIDIOC_REQBUFS`, `VIDIOC_QBUF`, `VIDIOC_DQBUF`,
`VIDIOC_STREAMON`), буферы отображаются в память через `mmap`, обмен идёт
через `poll`/`select`, освобождение — `munmap`/`close`.

**12. `VIDIOC_QUERYCAP`.**
Заполняет `struct v4l2_capability`: `driver` — имя драйвера (например,
`uvcvideo`), `card` — имя устройства («USB Camera»), `bus_info` — шина
(«usb-0000:00:14.0-5»), `version`, `capabilities` (проверка
`V4L2_CAP_VIDEO_CAPTURE`, `V4L2_CAP_STREAMING`).

**13. Форматы, разрешения и FPS в V4L2.**
`VIDIOC_ENUM_FMT` (`v4l2_fmtdesc`: `pixelformat`, `description`) —
форматы; для каждого формата `VIDIOC_ENUM_FRAMESIZES`
(`v4l2_frmsizeenum.discrete.width/height`) — разрешения; для каждой пары
`VIDIOC_ENUM_FRAMEINTERVALS`
(`v4l2_frmivalenum.discrete.numerator/denominator`) — интервалы, FPS =
denominator/numerator. Перечисление завершается, когда ioctl возвращает
`EINVAL`; индекс увеличивается вручную.

**14. Захват через mmap.**
`VIDIOC_REQBUFS` (count, `V4L2_MEMORY_MMAP`) → для каждого буфера
`VIDIOC_QUERYBUF` + `mmap` → `VIDIOC_QBUF` (поставить в очередь) →
`VIDIOC_STREAMON` → ожидание `poll` → `VIDIOC_DQBUF` (получить индекс и
`bytesused`) → обработка данных в `buffers[buf.index]` → снова `VIDIOC_QBUF`.
Завершение: `VIDIOC_STREAMOFF`, `munmap`, `close`.

**15. Сохранение MJPEG / YUYV / RGB24.**
MJPEG: буфер уже содержит готовый JPEG — достаточно записать `bytesused`
байт в файл `.jpg`. YUYV: нужно преобразовать в RGB/BGR (или сохранить как
PPM/BMP, дописав заголовок), учитывая субдискретизацию яркости/цветности.
RGB24: сохранить с заголовком BMP/PPM; из-за порядка BGR/RGB и выравнивания
строк возможны перестановки байт.

**16. Запись видео в Linux без FFmpeg.**
Варианты: (1) сохранять последовательность JPEG-кадров (`frame_00001.jpg`),
затем склеивать; (2) вручную формировать AVI-контейнер (RIFF: `hdrl` с
`avih`/`strh`/`strf` для MJPG, `movi` с чанками `00dc`, затем `idx1`-индекс) —
именно так устроен MJPEG-AVI; (3) писать необработанные кадры (raw) с
последующей обработкой; (4) pipe в `ffmpeg` (допустимо как внешний инструмент,
а не как API-библиотека).

**17. Отслеживание камеры в Linux.**
udev — монитор Netlink: `udev_monitor_new_from_netlink`,
`udev_monitor_filter_add_match_subsystem_devtype("video4linux")`, `poll` по fd;
события `add`/`remove`. inotify на `/dev` (IN_CREATE/IN_DELETE) — проще, но
не даёт свойств устройства и может пропускать события. Опрос `sysfs`
(`/sys/class/video4linux/`) — самый простой, но с задержкой и нагрузкой.
udev — предпочтителен.

**18. Глобальные горячие клавиши в Linux.**
X11: `XGrabKey(display, keycode, modifiers, root, True, GrabModeAsync,
GrabModeAsync)` на корневом окне; события `KeyPress` приходят даже при
неактивном окне; нужен `XKeysymToKeycode`/`XStringToKeysym`. evdev: чтение
`/dev/input/event*` — требует root или членства в группе `input`; зато
работает без X (в консоли). В Wayland глобальные клавиши через X11-механизмы
не работают — нужны порталы (`org.freedesktop.portal.GlobalShortcuts`).

**19. Многопоточный захват с нескольких камер.**
Для каждой камеры — свой `fd`/объект `ICamera` и свой поток (или общий пул с
`poll` на нескольких fd). Кадры складываются в отдельные кольцевые буферы,
GUI отрисовывает их по сообщениям/таймеру. Проблемы: гонки при доступе к
буферам (нужны мьютексы/атомарные обмены указателей), разная частота кадров,
синхронизация временных меток, конкуренция за USB-контроллер (пропускная
способность делится между камерами), блокирующие вызовы при отключении
устройства (нужны таймауты и переподключение).

**20. Почему запрещены OpenCV/GStreamer/FFmpeg API.**
Цель работы — изучение системных API (`open/ioctl/mmap`, DirectShow/MF), а
высокоуровневые библиотеки скрывают эти механизмы. Прямое использование
системных API даёт: понимание реальных ограничений (форматы, буферы,
синхронизация), меньший размер зависимости, отсутствие «чёрного ящика» при
отладке, возможность тонкой настройки (например, выбор MJPG вместо YUY2).
В данной работе OpenCV применён только как средство захвата/кодирования по
согласованию с преподавателем; скрытый режим, трей, горячие клавиши, журнал,
мониторинг устройств и работа с файлами реализованы системными средствами
(перечисление камер — через DirectShow `ICreateDevEnum`, а не через OpenCV).
